# 앱스토어 리뷰 요청(OS 네이티브 리뷰창) - 설계 (Design)

작성일: 2026-08-10
브랜치: `develop`에서 시작

## Context

앱에 사용자 리뷰를 늘리기 위해 OS가 제공하는 네이티브 리뷰창(iOS `SKStoreReviewController`,
Android In-App Review API)을 붙인다. 기능 자체는 패키지 한 줄 호출이라 단순하고, **설계의 핵심은
"언제 띄우는가"** 하나다.

### 플랫폼 제약 (설계 전제)

- **표시 여부를 앱이 알 수 없다.** iOS/Android 모두 요청 API는 성공/실패만 돌려주고, 리뷰창이 실제로
  떴는지, 사용자가 별점을 매겼는지 알려주지 않는다. 앱이 기록할 수 있는 건 "요청을 시도했다"까지다.
- **시스템 쿼터가 있다.** iOS는 앱당 365일 최대 3회, Android는 비공개 쿼터. 초과분은 조용히 삼켜진다.
- **리뷰창은 조작할 수 없다.** 별점 UI를 앞뒤로 감싸거나 "높은 점수를 눌러달라"고 유도하는 것은 양대
  스토어 심사 지침 위반이다.
- 웹은 지원 대상이 아니다(no-op).

## 확정된 결정 (사용자 확인)

- **목표**: 리뷰 수 확보 우선.
- **재요청**: 하지 않는다. 설치당 **최초 1회**만 요청하고 이후 영구히 스킵.
- **트리거 신호**: 일정 누적 개수 + 앱 실행 횟수/사용 일수. (일정 공유, 후원 결제는 제외)
- **노출 지점**: 하이브리드. 일정 저장 직후와 앱 시작 프롬프트 체인 끝, 두 곳.
- **기준치**: 균형 프리셋(아래 정책 참조).
- **상태 추적**: 일정 개수는 별도 카운터 없이 기존 `events_v1`의 **현재 보유 개수**로 판정.
- **원격 제어**: 킬스위치(on/off)만. 임계값은 앱에 하드코딩.

### 되돌릴 수 없는 선택이라는 점

"최초 1회"는 소진하면 회복이 없다. 시스템이 쿼터로 프롬프트를 삼켜도 앱은 알 수 없으므로 그 사용자는
영영 리뷰창을 못 본다. 이 리스크는 사용자에게 고지했고, 사용자 피로도를 우선해 1회로 확정했다.
그래서 킬스위치를 둔다 - 기준치가 잘못됐다고 판단되면 재배포 없이 즉시 끄고 다음 버전에서 고친다.

## 정책

```
게이트 (모두 AND)
  ├ 웹이 아님 (iOS/Android만)
  ├ 서버 킬스위치가 켜져 있음 (기본값: 켜짐)
  ├ 추적 시작 후 7일 경과
  ├ 앱을 사용한 날짜가 서로 다른 3일 이상 (연속일 필요 없음)
  └ 아직 리뷰를 요청한 적 없음 (영구)

트리거 (둘 중 하나라도 만족)
  ├ 저장된 일정이 5개 이상
  └ 앱 실행(콜드 스타트) 8회 이상
```

### "설치 후 7일"이 아니라 "추적 시작 후 7일"인 이유

기존 설치일을 알 방법이 없다. 기록이 없는 사용자는 이 기능이 담긴 버전을 처음 실행한 시각을 기준으로
삼는다. 결과적으로 **배포 후 최소 7일간은 아무에게도 리뷰창이 뜨지 않고**, 그 뒤부터 조건 충족자가
순차적으로 나온다. 신기능 배포 직후 대량 노출을 막는 안전장치 역할도 겸한다.

### 트리거와 노출 지점을 매핑하지 않는다

두 트리거는 OR이고, **두 노출 지점 모두에서 동일한 단일 판정 함수를 호출한다.** "일정 5개는 저장
직후에만, 실행 8회는 시작 시에만" 식으로 묶지 않는다. 이유:

- 판정 함수가 하나뿐이라 조건 분기와 테스트 조합이 절반으로 준다.
- 기회를 최대화한다. 기존 사용자는 이미 일정이 5개 이상일 수 있는데, 트리거를 저장 직후로 묶으면
  일정을 더 만들지 않는 한 영영 노출되지 않는다.
- 두 노출 지점 모두 "작업이 끝난 조용한 순간"이라 어느 쪽에서 떠도 흐름을 방해하지 않는다.

어느 지점에서 발동했는지는 애널리틱스 파라미터로만 구분한다.

## 설계

### 1) 신규 모듈 - `lib/features/app_review/`

기존 `app_update`(service + providers)와 `backup_reminder`(순수 판정 함수 + I/O 래퍼) 패턴을 따른다.
플랫폼/저장소에 의존하지 않는 판정 로직을 순수 함수로 떼어내 테스트 가능하게 만드는 것이 이 코드베이스의
방식이다.

```
lib/features/app_review/
  app_review_policy.dart    임계값 상수 + 순수 함수 shouldRequestReview(...)
  app_review_prefs.dart     SharedPreferences 읽기/쓰기 (키 5개)
  app_review_service.dart   recordLaunch() / maybeRequestAppReview() - I/O + 플랫폼 호출 + 로깅
```

### 2) 판정 - `app_review_policy.dart`

```dart
const kReviewMinDaysSinceTrackingStart = 7;
const kReviewMinUsageDays = 3;
const kReviewMinEventCount = 5;
const kReviewMinLaunchCount = 8;

bool shouldRequestReview({
  required DateTime now,
  required bool remoteEnabled,
  required DateTime? trackingStartedAt,
  required DateTime? requestedAt,
  required int usageDays,
  required int launchCount,
  required int eventCount,
});
```

순서대로: `requestedAt != null`이면 false(영구 1회) -> `!remoteEnabled`면 false -> `trackingStartedAt`이
null이거나 `now.difference(...) < 7일`이면 false -> `usageDays < 3`이면 false -> 마지막으로
`eventCount >= 5 || launchCount >= 8`을 반환. 플랫폼 판별(`kIsWeb`)은 호출부가 담당한다.

### 3) 상태 저장 - `app_review_prefs.dart`

`shared_preferences` 키 5개. 기존 `BackupPrefs`의 `readInstant`/`writeNow`와 같은 스타일로 ISO8601
문자열을 쓴다.

| 키 | 타입 | 용도 |
|---|---|---|
| `review_tracking_started_at` | ISO8601 String | 추적 시작 시각. 없으면 첫 `recordLaunch`에서 심는다 |
| `review_launch_count` | int | 콜드 스타트마다 +1 |
| `review_usage_days` | int | 날짜가 바뀐 실행에서만 +1 |
| `review_last_usage_day` | `yyyy-MM-dd` String | 위 카운터의 같은 날 중복 증가 방지 |
| `review_requested_at` | ISO8601 String | 요청 시도 시각. 존재하면 영구 스킵 |

일정 개수는 저장하지 않는다. 판정 시 `eventStoreProvider`의 `Map<String, List<CalendarEvent>>`에서
전체 일정 수를 세어 파생한다(날짜 키별 리스트 길이의 합). 반복 일정은 저장된 엔트리가 하나이므로
회차 수와 무관하게 **1개로 센다.**

### 4) 카운팅 - `recordLaunch()`

`lib/app/app.dart`의 `initState` 첫 프레임 콜백에서 **무조건 1회** 호출한다. 시작 프롬프트 체인
(`_runStartupPrompts`)이 아니라 그 바깥이다. 공유 딥링크로 진입해 프롬프트가 억제되는 경우에도 카운트는
쌓여야 하기 때문이다.

하는 일: `trackingStartedAt`이 없으면 now로 심고, `launchCount`를 +1 하고, `lastUsageDay`가 오늘과 다르면
`usageDays`를 +1 하고 `lastUsageDay`를 오늘로 갱신한다. `kIsWeb`이면 아무것도 하지 않는다.

앱이 백그라운드에 갔다 돌아오는 것은 카운트하지 않는다. `initState`는 콜드 스타트당 1회만 실행되므로
별도 처리가 필요 없다.

**순서 보장이 필요하다.** `recordLaunch()`는 `SharedPreferences`를 await하는 비동기 작업이고,
`_runStartupPrompts()`도 같은 첫 프레임 타이밍에 시작된다. 카운터 증가가 끝나기 전에 판정이 돌면
8번째 실행에서 `launchCount`를 7로 읽어 발동을 한 번 놓친다. 따라서 `recordLaunch()`가 반환한 Future를
필드(`_launchRecorded`)에 보관하고, `maybeRequestAppReview` 호출 직전에 이를 await한다.

### 5) 노출 지점 (a) - 앱 시작

`lib/app/app.dart` `_runStartupPrompts()` 맨 끝, `_checkAppUpdate()` 다음에 `maybeRequestAppReview`를
붙인다.

여기에 **기존 코드 변경이 하나 필요하다.** 현재 `maybeShowBackupRestoreNotice` /
`maybeShowBackupReminder` / `_checkAppUpdate`는 모두 `Future<void>`라 팝업이 실제로 떴는지 알 수 없다.
한 세션에 백업 팝업 -> 업데이트 팝업 -> 리뷰창을 연달아 띄우면 최악이므로, 세 함수가
**`Future<bool>`(표시 여부)을 반환**하도록 바꾸고 앞에서 하나라도 떴으면 리뷰는 이번 세션을 건너뛴다.

리뷰 전용 플래그를 따로 두는 대안도 있으나, 그러면 각 팝업이 "내가 떴다"를 어딘가에 기록해야 해서 더
지저분해진다. 반환값을 쓰는 쪽이 데이터 흐름이 명시적이다.

기존 `_suppressStartupPromptsForShare` 가드는 그대로 적용받는다(공유 링크 진입 시 리뷰도 억제).

### 6) 노출 지점 (b) - 일정 저장 직후

`lib/features/events/presentation/event_editor_sheet.dart`.

`showEventEditor` 호출부가 4곳(`calendar_page.dart`, `day_detail_view.dart` 2곳, `app.dart`)이라 각각에
훅을 달면 흩어진다. 대신:

1. `_EventEditorPage`가 **신규 저장 성공 시** `Navigator.pop(true)`로 저장 여부를 반환한다.
2. `showEventEditor` 함수 내부에서 그 결과를 받아, `true`면 `maybeRequestAppReview`를 호출한다.
3. 호출부 4곳은 수정하지 않는다(`showEventEditor`의 시그니처는 `Future<void>` 유지).

수정과 삭제는 발동시키지 않는다. 저장 직후 에디터 페이지는 이미 pop된 상태이므로 리뷰창은 달력 화면
위에 뜬다.

**Riverpod 접근 방식:** `showEventEditor`는 `BuildContext`만 받고 `WidgetRef`를 받지 않는다. 에디터
페이지의 `ref`는 pop 이후 dispose되므로 쓸 수 없다. 따라서 `maybeRequestAppReview`는 `WidgetRef`가
아니라 **`ProviderContainer`를 받도록** 하고, 호출부에서 `ProviderScope.containerOf(context)`로 얻는다
(`showEventEditor`에 전달된 context는 호출부인 달력 화면의 것이라 pop 이후에도 유효하다). 앱 시작 지점
(5번)도 같은 방식으로 통일한다. 호출부 4곳의 시그니처는 그대로 둘 수 있다.

### 7) 킬스위치 - `app_metadata_service.dart`

`AppMetadata`에 `reviewPromptEnabled` 필드를 추가하고 `/app/metadata` 응답의 `review.enabled`를 읽는다.

```json
{ "giftShop": { ... }, "review": { "enabled": true } }
```

**필드가 없거나, 파싱에 실패하거나, 서버 요청 자체가 실패하면 `true`**로 둔다(`AppMetadata.fallback`
포함). 서버 장애가 기능을 죽이지 않게 하기 위해서다. 앱은 이미 `initState`에서
`appMetadataProvider`를 prefetch하므로 판정 시점에는 캐시에서 즉시 나온다. 판정부는
`ref.read(appMetadataProvider.future)`로 await하되, `AppMetadataService.fetch`에 이미 4초 타임아웃과
fallback이 걸려 있어 무한 대기는 없다.

서버 측 `review.enabled` 응답 추가는 별도 작업 항목이다. 서버가 이 필드를 안 내려주는 동안에도 앱은
정상 동작한다(true fallback).

### 8) 플랫폼 호출 - `app_review_service.dart`

`in_app_review: ^2.0.12` 패키지를 추가한다.

```dart
final review = InAppReview.instance;
if (!await review.isAvailable()) return;   // 기록도 남기지 않는다
await review.requestReview();
await AppReviewPrefs.writeRequestedAt(prefs, now);
```

- `isAvailable()`이 false면 기록 없이 종료한다. 다음 기회에 다시 시도할 수 있어야 한다.
- `requestReview()`가 예외를 던지면 `requestedAt`을 기록하지 않고 조용히 삼킨다(`debugPrint`만).
- `openStoreListing` 폴백은 쓰지 않는다. 사용자를 앱 밖으로 밀어내는 것은 요청하지 않은 동작이다.

### 9) 측정 - Firebase Analytics

`app_review_requested` 이벤트를 요청 시도 시 1회 기록한다.

| 파라미터 | 값 |
|---|---|
| `entry` | `startup` \| `event_saved` (어느 노출 지점에서 발동했는지) |
| `matched` | `event_count` \| `launch_count` \| `both` (어느 트리거가 만족했는지) |

**이 이벤트는 "요청 시도" 수이지 "리뷰창 표시" 수가 아니다.** 실제 효과는 스토어 콘솔의 리뷰 수 추이로
간접 확인한다. 이 한계는 플랫폼 제약이라 우회할 수 없다.

## 범위 밖 (YAGNI)

- 재요청, 쿨다운, 버전 기반 재노출.
- 리뷰창 앞에 "앱이 마음에 드시나요?"를 묻는 2단계 게이팅. 스토어 심사 지침 위반 소지가 있다.
- 원격 임계값 조정, A/B 테스트.
- 설정 화면의 "앱 평가하기" 수동 메뉴(현재 없음). 별개 기능으로 필요하면 따로 다룬다.
- 일정 공유/후원 결제 트리거.
- 안드로이드/iOS별 다른 기준치.

## 검증 (End-to-End)

1. 단위(`shouldRequestReview`) - 경계값:
   - 경과일 6일 false / 7일 true
   - 사용일 2일 false / 3일 true
   - 일정 4개+실행 7회 false / 일정 5개 true / 실행 8회 true
   - `requestedAt`이 있으면 다른 조건이 모두 충족돼도 false
   - `remoteEnabled=false`면 false
   - `trackingStartedAt=null`이면 false
2. 단위(`AppReviewPrefs`) - 같은 날 두 번 `recordLaunch` 시 `usageDays`는 1회만 증가하고 `launchCount`는
   2 증가.
3. 단위(`AppMetadata.fromJson`) - `review` 없음 / `review.enabled=false` / 잘못된 타입 각각에 대해
   `reviewPromptEnabled`가 true/false/true.
4. 위젯 - 신규 일정 저장 시 `showEventEditor`가 pop 결과 `true`를 받고, 수정/삭제/취소에서는 받지 않음.
5. 수동 - 실기기에서 `requestedAt`을 지우고 임계값을 낮춘 디버그 빌드로 리뷰창 실제 노출 확인
   (iOS는 TestFlight/디버그 빌드에서만 항상 뜨고, 프로덕션에서는 쿼터가 적용된다).
6. `flutter analyze` 무경고, `flutter test` 통과.
