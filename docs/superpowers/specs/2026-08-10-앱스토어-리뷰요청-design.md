# 앱스토어 리뷰 요청(OS 네이티브 리뷰창) - 설계 (Design)

작성일: 2026-08-10
브랜치: `feature/리뷰`

## Context

앱에 사용자 리뷰를 늘리기 위해 OS가 제공하는 네이티브 리뷰창(iOS `SKStoreReviewController`,
Android In-App Review API)을 붙인다. 기능 자체는 패키지 한 줄 호출이라 단순하고, **설계의 핵심은
"언제 띄우는가"** 하나다.

### 플랫폼 제약 (설계 전제)

- **표시 여부를 앱이 알 수 없다.** iOS/Android 모두 요청 API는 성공/실패만 돌려주고, 리뷰창이 실제로
  떴는지, 사용자가 별점을 매겼는지 알려주지 않는다. 앱이 기록할 수 있는 건 "요청을 시도했다"까지다.
- **시스템 쿼터가 있다.** iOS는 앱당 365일 최대 3회, Android는 비공개 쿼터. 초과분은 조용히 삼켜진다.
- **리뷰창은 조작할 수 없다.** 별점 UI를 앞뒤로 감싸거나 "높은 점수를 눌러달라"고 유도하는 것은 양대
  스토어 심사 지침 위반이다.
- 웹은 지원 대상이 아니다(no-op).

## 정책

```
모두 AND - 하나라도 어긋나면 요청하지 않는다

  ├ iOS/Android (웹 no-op)
  ├ 서버 킬스위치가 켜져 있음 (기본값: 켜짐)
  ├ 앱 설치 후 7일 경과
  ├ 앱 실행(세션) 8회 이상
  ├ 저장된 일정이 5개 이상
  └ 아직 리뷰를 요청한 적 없음 (영구 1회)

노출 시점
  └ 일정 저장 직후, 오직 이때만
```

## 확정된 결정 (사용자 확인)

- **재요청**: 하지 않는다. 설치당 **최초 1회**만 요청하고 이후 영구히 스킵.
- **조건 결합**: 세 조건(설치 7일 / 실행 8회 / 일정 5개)을 **AND**로 묶는다.
- **노출 시점**: **일정 저장 직후 한 곳뿐.** 앱 시작 시점에는 띄우지 않는다.
- **경과일 기준**: **실제 앱 설치 시각**(`PackageInfo.installTime`).
- **실행 1회의 정의**: 세션 기준. 콜드 스타트 + 백그라운드에 30분 이상 있다가 복귀.
- **일정 개수**: 별도 카운터 없이 기존 `events_v1`의 **현재 보유 개수**로 판정.
- **원격 제어**: 킬스위치(on/off)만. 임계값은 앱에 하드코딩.
- **제외한 조건**: "서로 다른 3일 이상 사용" 게이트는 두지 않는다. 실행 8회가 같은 신호를 거의 흡수해
  조건만 늘고 걸러내는 사용자는 겹친다.

### 노출 시점을 일정 저장 직후로만 한정한 이유

앱을 열어보기만 한 사용자에게 리뷰를 청하는 것은 과하다. 리뷰는 **앱을 실제로 활용한 사람**에게 받아야
의미가 있고, "최초 1회"뿐인 기회를 조회만 하는 사용자에게 소모할 이유가 없다.

이 결정의 부수 효과로 **기존 코드 수정 범위가 크게 줄었다.** 앱 시작 프롬프트 체인
(`_runStartupPrompts`)에 손댈 필요가 없어져, 초안에 있던 "백업 팝업/업데이트 팝업 함수들을
`Future<bool>`로 바꿔 중복 노출을 조율한다"는 작업이 통째로 사라졌다. 일정 저장은 시작 팝업들이 모두
닫힌 뒤에 일어나므로 겹칠 일이 없다.

대신 **이미 일정을 5개 넘게 가진 사용자는 다음 일정을 저장할 때** 노출된다. 5개에서 멈추고 더 만들지
않으면 노출되지 않는다. 이는 의도된 동작이다.

### "설치 후 7일"은 진짜 설치 시점 기준이다

`package_info_plus` 10.2.1의 `PackageInfo.installTime`을 쓴다. 소스를 확인한 결과:

- **Android**: `PackageManager.firstInstallTime`. OS가 주는 정확한 값. 앱 업데이트로는 바뀌지 않고,
  삭제 후 재설치하면 갱신된다.
- **iOS**: 공식 API가 없어 **Documents 디렉터리(`NSDocumentDirectory`)의 생성일**을 반환한다. 공식
  보장이 아닌 휴리스틱이지만 업데이트로는 바뀌지 않는다. 기기 이전이나 백업 복원 시 복원 시점으로
  잡힐 수 있는데, 이는 "더 늦게 뜬다"는 안전한 방향이라 문제되지 않는다.
- 웹에서는 `null`이며, 이 경우 요청하지 않는다.

### 실행 횟수는 설치 시점부터 소급할 수 없다

OS는 앱 실행 횟수를 기록해주지 않는다. 앱이 직접 세야 하므로 **이 기능이 담긴 버전을 배포한 뒤부터만**
카운트된다. 결과적으로 조건별 소급 가능 여부는 다음과 같다.

| 조건 | 설치 시점부터 소급 | 근거 |
|---|---|---|
| 설치 후 7일 | 가능 | OS가 설치 시각 제공 |
| 일정 5개 | 가능 | 현재 보유 개수를 세므로 기존 일정 포함 |
| 실행 8회 | **불가능** | 앱이 직접 세야 함. 배포 이후부터 누적 |

즉 오래된 사용자는 설치 경과일과 일정 개수를 즉시 통과하고 **실행 횟수만 새로 쌓는다.** 이것이 가능한
최선이며, 신기능 배포 직후 대량 노출을 막는 효과도 겸한다.

## 설계

### 1) 신규 모듈 - `lib/features/app_review/`

기존 `app_update`(service + providers)와 `backup_reminder`(순수 판정 함수 + I/O 래퍼) 패턴을 따른다.
플랫폼/저장소에 의존하지 않는 판정 로직을 순수 함수로 떼어내 테스트 가능하게 만드는 것이 이 코드베이스의
방식이다.

```
lib/features/app_review/
  app_review_policy.dart    임계값 상수 + 순수 함수 shouldRequestReview(), isNewSession()
  app_review_prefs.dart     SharedPreferences 읽기/쓰기 (키 2개)
  app_review_service.dart   recordSession() / maybeRequestAppReview() - I/O + 플랫폼 호출 + 로깅
```

### 2) 판정 - `app_review_policy.dart`

```dart
const kReviewMinDaysSinceInstall = 7;
const kReviewMinSessionCount = 8;
const kReviewMinEventCount = 5;
const kReviewSessionGap = Duration(minutes: 30);

bool shouldRequestReview({
  required DateTime now,
  required bool remoteEnabled,
  required DateTime? installedAt,
  required DateTime? requestedAt,
  required int sessionCount,
  required int eventCount,
});

/// 백그라운드 복귀를 새 세션으로 볼지 판정한다.
bool isNewSession({
  required DateTime now,
  required DateTime? lastPausedAt,
  Duration gap = kReviewSessionGap,
});
```

`shouldRequestReview`는 순서대로 검사해 하나라도 걸리면 false를 반환한다: `requestedAt != null`(영구
1회) -> `!remoteEnabled` -> `installedAt == null` -> `now.difference(installedAt) < 7일` ->
`sessionCount < 8` -> `eventCount < 5`. 전부 통과하면 true. 플랫폼 판별(`kIsWeb`)은 호출부가 담당한다.

`isNewSession`은 `lastPausedAt`이 null이면 false(아직 백그라운드에 간 적 없음), 아니면
`now.difference(lastPausedAt) >= gap`을 반환한다.

### 3) 상태 저장 - `app_review_prefs.dart`

`shared_preferences` 키 2개면 충분하다. 설치 시각은 OS에서 오고, 일정 개수는 기존 저장소에서 파생하기
때문이다. 기존 `BackupPrefs`의 `readInstant`/`writeNow`와 같은 스타일로 ISO8601 문자열을 쓴다.

| 키 | 타입 | 용도 |
|---|---|---|
| `review_session_count` | int | 세션마다 +1 |
| `review_requested_at` | ISO8601 String | 요청 시도 시각. 존재하면 영구 스킵 |

마지막 백그라운드 진입 시각(`lastPausedAt`)은 **저장하지 않고 메모리 필드로 둔다.** 프로세스가 죽으면
다음 진입은 콜드 스타트라 어차피 세션 1회로 세어지므로, 디스크에 남길 이유가 없다.

일정 개수는 판정 시 `eventStoreProvider`의 `Map<String, List<CalendarEvent>>`에서 전체 일정 수를 세어
파생한다(날짜 키별 리스트 길이의 합). 반복 일정은 저장된 엔트리가 하나이므로 회차 수와 무관하게
**1개로 센다.**

### 4) 세션 카운팅 - `lib/app/app.dart`

`_CatholicCalendarAppState`에 `WidgetsBindingObserver`를 mixin으로 붙인다(현재는 없다).

- `initState`의 첫 프레임 콜백에서 `recordSession()`을 **무조건 1회** 호출한다. 시작 프롬프트 체인
  바깥이라, 공유 딥링크로 진입해 프롬프트가 억제되는 경우에도 세션은 쌓인다.
- `didChangeAppLifecycleState`에서 `paused`면 `_lastPausedAt = DateTime.now()`를 기록하고, `resumed`면
  `isNewSession(...)`이 true일 때만 `recordSession()`을 호출한다.
- `initState`에서 `addObserver(this)`, `dispose`에서 `removeObserver(this)`.
- `kIsWeb`이면 아무것도 하지 않는다.

**순서 보장이 필요하다.** `recordSession()`은 `SharedPreferences`를 await하는 비동기 작업이라, 앱을 열자마자
일정을 저장하면 카운터 증가 전에 판정이 돌아 8번째 세션을 놓칠 수 있다. `app_review_service.dart` 내부에
진행 중인 Future를 보관하고(`Future<void>? _sessionRecording`), `maybeRequestAppReview`가 판정 전에 이를
await한다. 서비스 파일 안에 캡슐화되므로 호출부는 신경 쓸 필요가 없다.

### 5) 노출 - `event_editor_sheet.dart`

`showEventEditor` 호출부가 4곳(`calendar_page.dart`, `day_detail_view.dart` 2곳, `app.dart`)이라 각각에
훅을 달면 흩어진다. 대신:

1. `_EventEditorPage`가 **신규 저장 성공 시** `Navigator.pop(true)`로 저장 여부를 반환한다.
2. `showEventEditor` 함수 내부에서 그 결과를 받아, `true`면 `maybeRequestAppReview`를 호출한다.
3. 호출부 4곳은 수정하지 않는다(`showEventEditor`의 시그니처는 `Future<void>` 유지).

수정과 삭제는 발동시키지 않는다. 저장 직후 에디터 페이지는 이미 pop된 상태이므로 리뷰창은 달력 화면
위에 뜬다.

**Riverpod 접근 방식:** `showEventEditor`는 `BuildContext`만 받고 `WidgetRef`를 받지 않는다. 에디터
페이지의 `ref`는 pop 이후 dispose되므로 쓸 수 없다. 따라서 `maybeRequestAppReview`는 `WidgetRef`가
아니라 **`ProviderContainer`를 받도록** 하고, 호출부에서 `ProviderScope.containerOf(context)`로 얻는다
(`showEventEditor`에 전달된 context는 호출부인 달력 화면의 것이라 pop 이후에도 유효하다). 호출부 4곳의
시그니처는 그대로 둘 수 있다.

### 6) 킬스위치 - `app_metadata_service.dart`

`AppMetadata`에 `reviewPromptEnabled` 필드를 추가하고 `/app/metadata` 응답의 `review.enabled`를 읽는다.

```json
{ "giftShop": { ... }, "review": { "enabled": true } }
```

**필드가 없거나, 파싱에 실패하거나, 서버 요청 자체가 실패하면 `true`**로 둔다(`AppMetadata.fallback`
포함). 서버 장애가 기능을 죽이지 않게 하기 위해서다. 앱은 이미 `initState`에서
`appMetadataProvider`를 prefetch하므로 판정 시점에는 캐시에서 즉시 나온다. 판정부는
`container.read(appMetadataProvider.future)`로 await하되, `AppMetadataService.fetch`에 이미 4초
타임아웃과 fallback이 걸려 있어 무한 대기는 없다.

서버 측 `review.enabled` 응답 추가는 별도 작업 항목이다. 서버가 이 필드를 안 내려주는 동안에도 앱은
정상 동작한다(true fallback).

### 7) 플랫폼 호출 - `app_review_service.dart`

`in_app_review: ^2.0.12` 패키지를 추가한다.

```dart
final review = InAppReview.instance;
if (!await review.isAvailable()) return;   // 기록도 남기지 않는다
await review.requestReview();
await AppReviewPrefs.writeRequestedAt(prefs, now);
```

- `isAvailable()`이 false면 기록 없이 종료한다. 다음 기회에 다시 시도할 수 있어야 한다.
- `requestReview()`가 예외를 던지면 `requestedAt`을 기록하지 않고 조용히 삼킨다(`debugPrint`만).
- `openStoreListing` 폴백은 쓰지 않는다. 사용자를 앱 밖으로 밀어내는 것은 요청하지 않은 동작이다.

### 8) 측정 - Firebase Analytics

요청 시도 시 `app_review_requested` 이벤트를 1회 기록한다. 노출 지점이 한 곳뿐이라 파라미터는 두지
않는다.

**이 이벤트는 "요청 시도" 수이지 "리뷰창 표시" 수가 아니다.** 실제 효과는 스토어 콘솔의 리뷰 수 추이로
간접 확인한다. 이 한계는 플랫폼 제약이라 우회할 수 없다.

## 주요 파일

- 신규: `lib/features/app_review/app_review_policy.dart`, `app_review_prefs.dart`,
  `app_review_service.dart`, `test/app_review_policy_test.dart`.
- 수정:
  - `pubspec.yaml` - `in_app_review` 추가
  - `lib/app/app.dart` - `WidgetsBindingObserver` mixin + 세션 카운팅
  - `lib/features/events/presentation/event_editor_sheet.dart` - pop 결과 + 리뷰 호출
  - `lib/features/app_metadata/app_metadata_service.dart` - `reviewPromptEnabled`
- 서버(별도): `/app/metadata` 응답에 `review.enabled` 추가.

기존 프롬프트 체인(`backup_notice.dart`, `backup_reminder.dart`, `_runStartupPrompts`)은 **건드리지
않는다.**

## 범위 밖 (YAGNI)

- 앱 시작 시점 노출, 그에 따른 기존 팝업 함수의 `Future<bool>` 전환.
- "서로 다른 N일 사용" 게이트.
- 재요청, 쿨다운, 버전 기반 재노출.
- 리뷰창 앞에 "앱이 마음에 드시나요?"를 묻는 2단계 게이팅. 스토어 심사 지침 위반 소지가 있다.
- 원격 임계값 조정, A/B 테스트.
- 설정 화면의 "앱 평가하기" 수동 메뉴(현재 없음). 별개 기능으로 필요하면 따로 다룬다.
- 일정 공유/후원 결제 트리거.
- 안드로이드/iOS별 다른 기준치.

## 검증 (End-to-End)

1. 단위(`shouldRequestReview`) - AND 결합이므로 각 조건을 하나씩 떨어뜨려 false가 되는지 확인:
   - 설치 경과 6일 false / 7일 true
   - 세션 7회 false / 8회 true
   - 일정 4개 false / 5개 true
   - `requestedAt`이 있으면 다른 조건이 모두 충족돼도 false
   - `remoteEnabled=false`면 false
   - `installedAt=null`이면 false
2. 단위(`isNewSession`) - `lastPausedAt=null` false / 29분 false / 30분 true / 31분 true.
3. 단위(`AppReviewPrefs`) - `recordSession` 2회 호출 시 `review_session_count`가 2 증가.
4. 단위(`AppMetadata.fromJson`) - `review` 없음 / `review.enabled=false` / 잘못된 타입 각각에 대해
   `reviewPromptEnabled`가 true/false/true.
5. 위젯 - 신규 일정 저장 시 `showEventEditor`가 pop 결과 `true`를 받고, 수정/삭제/취소에서는 받지 않음.
6. 수동 - 실기기에서 `review_requested_at`을 지우고 임계값을 낮춘 디버그 빌드로 리뷰창 실제 노출 확인
   (iOS는 TestFlight/디버그 빌드에서만 항상 뜨고, 프로덕션에서는 쿼터가 적용된다).
7. `flutter analyze` 무경고, `flutter test` 통과.
