# 앱스토어 리뷰 요청(OS 네이티브 리뷰창) - 설계 (Design)

작성일: 2026-08-10
브랜치: `feature/리뷰`

## Context

앱에 사용자 리뷰를 늘리기 위해 OS가 제공하는 네이티브 리뷰창(iOS `SKStoreReviewController`,
Android In-App Review API)을 붙인다. 기능 자체는 패키지 한 줄 호출이라 단순하고, **설계의 핵심은
"언제 띄우는가"** 하나다.

### 플랫폼 제약 (설계 전제)

- **표시 여부를 앱이 알 수 없다.** iOS/Android 모두 요청 API는 성공/실패만 돌려주고, 리뷰창이 실제로
  떴는지, 사용자가 별점을 매겼는지 알려주지 않는다. 앱이 기록할 수 있는 건 "요청을 시도했다"까지다.
- **사용자가 리뷰를 이미 썼는지도 알 수 없다.** 그건 OS만 안다. 앱은 리뷰 작성자와 미작성자를 구분할
  수 없고, 이미 쓴 사람에게 안 띄우는 판단은 시스템이 알아서 한다.
- **시스템 쿼터가 있다.** iOS는 앱당 365일 최대 3회, Android는 비공개 쿼터. 초과분은 조용히 삼켜진다.
- **리뷰창은 조작할 수 없다.** 별점 UI를 앞뒤로 감싸거나 "높은 점수를 눌러달라"고 유도하는 것은 양대
  스토어 심사 지침 위반이다.
- 웹은 지원 대상이 아니다(no-op).

## 정책

```
모두 AND - 하나라도 어긋나면 요청하지 않는다

  ├ iOS/Android (웹 no-op)
  ├ 서버 킬스위치가 켜져 있음 (기본값: 켜짐)
  ├ 저장된 일정이 5개 이상
  └ 아직 리뷰를 요청한 적 없음 (설치당 1회)

노출 시점
  └ 일정 저장 직후, 오직 이때만
```

시간 게이트(설치 후 N일)도, 실행 횟수 조건도 두지 않는다. **일정 5개를 채우는 것 자체가 앱을 실제로
쓰고 있다는 신호**이고, 조건을 하나로 줄이면 정책이 명확해지고 검증할 것도 적어진다.

## 확정된 결정 (사용자 확인)

- **조건**: 저장된 일정 5개 이상, 그것 하나뿐.
- **노출 시점**: **일정 저장 직후 한 곳뿐.** 앱 시작 시점에는 띄우지 않는다.
- **횟수**: 설치당 **1회**. 요청하고 나면 그 설치에서는 다시 요청하지 않는다.
- **리뷰 작성 여부는 구분하지 않는다.** 애초에 앱이 알 수 없다. 조건을 만족하면 작성 이력과 무관하게
  1회 요청하고, 이미 쓴 사람에게 안 띄우는 것은 시스템에 맡긴다.
- **일정 개수**: 별도 카운터 없이 기존 `events_v1`의 **현재 보유 개수**로 판정.
- **원격 제어**: 킬스위치(on/off)만. 임계값은 앱에 하드코딩.

### 노출 시점을 일정 저장 직후로만 한정한 이유

앱을 열어보기만 한 사용자에게 리뷰를 청하는 것은 과하다. 리뷰는 **앱을 실제로 활용한 사람**에게 받아야
의미가 있다.

이 결정의 부수 효과로 **기존 코드 수정 범위가 크게 줄었다.** 앱 시작 프롬프트 체인
(`_runStartupPrompts`)에 손댈 필요가 없고, `lib/app/app.dart`는 아예 건드리지 않는다. 일정 저장은 시작
팝업들이 모두 닫힌 뒤에 일어나므로 겹칠 일도 없다.

**5번째 일정을 저장하는 순간** 리뷰창이 뜬다. 이미 5개를 넘게 가진 사용자는 다음 일정을 저장할 때
뜬다. 5개에서 멈추고 더 만들지 않으면 뜨지 않는데, 이는 의도된 동작이다.

### 재설치하면 다시 노출된다 (조건부)

리뷰 요청 이력은 `shared_preferences`에 저장되고, 이것은 앱을 지우면 함께 사라진다. 따라서 재설치하면
초기화되어 일정 5개를 다시 채웠을 때 한 번 더 요청한다.

다만 **백업 복원으로 재설치한 경우는 예외**다. Android는 `AndroidManifest.xml`에 `allowBackup` 명시가
없어 기본값 `true`이므로 Auto Backup이 동작하고, 같은 Google 계정으로 재설치하면
`SharedPreferences`가 복원된다. iOS도 iCloud 백업 복원 시 `UserDefaults`가 복원된다. 이 경우 리뷰
요청 이력이 살아나 다시 요청하지 않는다.

**이 동작을 굳이 우회하지 않는다.** 백업이 복원됐다는 건 일정 데이터도 함께 복원돼 "이어서 쓰는 같은
사용자"라는 뜻이고, 그런 사용자에게 리뷰를 다시 청할 이유가 없다. 게다가 Flutter의
`shared_preferences`는 모든 키를 `FlutterSharedPreferences.xml` 파일 하나에 넣기 때문에, 리뷰 키만
백업에서 빼려면 일정 데이터까지 백업 대상에서 제외해야 한다. 대가가 이득보다 크다.

## 설계

### 1) 신규 모듈 - `lib/features/app_review/`

기존 `app_update`(2파일 구성)와 `backup_reminder`(순수 판정 함수 + I/O 래퍼) 패턴을 따른다.
플랫폼/저장소에 의존하지 않는 판정 로직을 순수 함수로 떼어내 테스트 가능하게 만드는 것이 이 코드베이스의
방식이다.

```
lib/features/app_review/
  app_review_policy.dart    임계값 상수 + 순수 함수 shouldRequestReview()
  app_review_service.dart   SharedPreferences I/O + 플랫폼 호출 + 로깅
```

조건이 하나뿐이라 저장 키도 하나여서, prefs 전용 파일은 만들지 않고 서비스에 둔다.

### 2) 판정 - `app_review_policy.dart`

```dart
const kReviewMinEventCount = 5;

bool shouldRequestReview({
  required bool remoteEnabled,
  required DateTime? requestedAt,
  required int eventCount,
}) {
  if (requestedAt != null) return false;   // 설치당 1회
  if (!remoteEnabled) return false;        // 서버 킬스위치
  return eventCount >= kReviewMinEventCount;
}
```

시간 조건이 없으므로 `now`를 받지 않는다. 플랫폼 판별(`kIsWeb`)은 호출부가 담당한다.

### 3) 상태 저장

`shared_preferences` 키 1개.

| 키 | 타입 | 용도 |
|---|---|---|
| `review_requested_at` | ISO8601 String | 요청 시도 시각. 존재하면 이 설치에서는 영구 스킵 |

기존 `BackupPrefs`의 `readInstant`/`writeNow`와 같은 스타일로 ISO8601 문자열을 쓴다. 판정에는 존재
여부만 쓰지만, 시각을 남겨두면 나중에 로그를 볼 때 언제 요청했는지 알 수 있다.

일정 개수는 저장하지 않는다. 판정 시 `eventStoreProvider`의 `Map<String, List<CalendarEvent>>`에서
전체 일정 수를 세어 파생한다(날짜 키별 리스트 길이의 합). 반복 일정은 저장된 엔트리가 하나이므로
회차 수와 무관하게 **1개로 센다.**

### 4) 노출 - `event_editor_sheet.dart`

`showEventEditor` 호출부가 4곳(`calendar_page.dart`, `day_detail_view.dart` 2곳, `app.dart`)이라 각각에
훅을 달면 흩어진다. 대신:

1. `_EventEditorPage`가 **신규 저장 성공 시** `Navigator.pop(true)`로 저장 여부를 반환한다.
2. `showEventEditor` 함수 내부에서 그 결과를 받아, `true`면 `maybeRequestAppReview`를 호출한다.
3. 호출부 4곳은 수정하지 않는다(`showEventEditor`의 시그니처는 `Future<void>` 유지).

수정과 삭제는 발동시키지 않는다. `Navigator.push`가 반환하는 Future는 pop 애니메이션이 끝난 뒤
완료되므로 리뷰창은 달력 화면 위에 뜨지만, 전환이 완전히 안정된 뒤 띄우도록 짧은 지연
(`Future.delayed(Duration(milliseconds: 400))`)을 한 번 준다.

**Riverpod 접근 방식:** `showEventEditor`는 `BuildContext`만 받고 `WidgetRef`를 받지 않는다. 에디터
페이지의 `ref`는 pop 이후 dispose되므로 쓸 수 없다. 따라서 `maybeRequestAppReview`는 `WidgetRef`가
아니라 **`ProviderContainer`를 받도록** 하고, 호출부에서 `ProviderScope.containerOf(context)`로 얻는다
(`showEventEditor`에 전달된 context는 호출부인 달력 화면의 것이라 pop 이후에도 유효하다). 호출부 4곳의
시그니처는 그대로 둘 수 있다.

### 5) 킬스위치 - `app_metadata_service.dart`

`AppMetadata`에 `reviewPromptEnabled` 필드를 추가하고 `/app/metadata` 응답의 `review.enabled`를 읽는다.

```json
{ "giftShop": { ... }, "review": { "enabled": true } }
```

**필드가 없거나, 파싱에 실패하거나, 서버 요청 자체가 실패하면 `true`**로 둔다(`AppMetadata.fallback`
포함). 서버 장애가 기능을 죽이지 않게 하기 위해서다. 앱은 이미 `initState`에서
`appMetadataProvider`를 prefetch하므로 판정 시점에는 캐시에서 즉시 나온다. 판정부는
`container.read(appMetadataProvider.future)`로 await하되, `AppMetadataService.fetch`에 이미 4초
타임아웃과 fallback이 걸려 있어 무한 대기는 없다.

서버 측 `review.enabled` 응답 추가는 별도 작업 항목이다. 서버가 이 필드를 안 내려주는 동안에도 앱은
정상 동작한다(true fallback).

### 6) 플랫폼 호출 - `app_review_service.dart`

`in_app_review: ^2.0.12` 패키지를 추가한다.

```dart
final review = InAppReview.instance;
if (!await review.isAvailable()) return;   // 기록도 남기지 않는다
await review.requestReview();
await _writeRequestedAt(prefs, DateTime.now());
```

- `isAvailable()`이 false면 기록 없이 종료한다. 설치당 1회뿐인 기회를 리뷰창이 뜰 수 없는 상황에
  소모하면 안 된다.
- `requestReview()`가 예외를 던지면 `requestedAt`을 기록하지 않고 조용히 삼킨다(`debugPrint`만).
  다음 저장 때 다시 시도한다.
- `openStoreListing` 폴백은 쓰지 않는다. 사용자를 앱 밖으로 밀어내는 것은 요청하지 않은 동작이다.

### 7) 측정 - Firebase Analytics

요청 시도 시 `app_review_requested` 이벤트를 1회 기록한다. 노출 지점이 한 곳뿐이라 파라미터는 두지
않는다.

**이 이벤트는 "요청 시도" 수이지 "리뷰창 표시" 수가 아니다.** 실제 효과는 스토어 콘솔의 리뷰 수 추이로
간접 확인한다. 이 한계는 플랫폼 제약이라 우회할 수 없다.

## 주요 파일

- 신규: `lib/features/app_review/app_review_policy.dart`, `app_review_service.dart`,
  `test/app_review_policy_test.dart`.
- 수정:
  - `pubspec.yaml` - `in_app_review` 추가
  - `lib/features/events/presentation/event_editor_sheet.dart` - pop 결과 + 리뷰 호출
  - `lib/features/app_metadata/app_metadata_service.dart` - `reviewPromptEnabled`
- 서버(별도): `/app/metadata` 응답에 `review.enabled` 추가.

`lib/app/app.dart`와 기존 프롬프트 체인(`backup_notice.dart`, `backup_reminder.dart`)은 **건드리지
않는다.**

## 범위 밖 (YAGNI)

- 설치 후 경과일 게이트, 앱 실행/세션 횟수 조건, 사용일 게이트.
- 앱 시작 시점 노출.
- 재요청, 쿨다운, 버전 기반 재노출.
- 백업 복원 시 리뷰 이력만 제외하기(위 "재설치하면 다시 노출된다" 참조).
- 리뷰창 앞에 "앱이 마음에 드시나요?"를 묻는 2단계 게이팅. 스토어 심사 지침 위반 소지가 있다.
- 원격 임계값 조정, A/B 테스트.
- 설정 화면의 "앱 평가하기" 수동 메뉴(현재 없음). 별개 기능으로 필요하면 따로 다룬다.
- 일정 공유/후원 결제 트리거.
- 안드로이드/iOS별 다른 기준치.

## 검증 (End-to-End)

1. 단위(`shouldRequestReview`) - AND 결합이므로 각 조건을 하나씩 떨어뜨려 false가 되는지 확인:
   - 일정 4개 false / 5개 true / 6개 true
   - `requestedAt`이 있으면 일정이 5개 이상이어도 false
   - `remoteEnabled=false`면 false
2. 단위(`AppMetadata.fromJson`) - `review` 없음 / `review.enabled=false` / 잘못된 타입 각각에 대해
   `reviewPromptEnabled`가 true/false/true.
3. 위젯 - 신규 일정 저장 시 `showEventEditor`가 pop 결과 `true`를 받고, 수정/삭제/취소에서는 받지 않음.
4. 수동 - 실기기에서 일정 4개까지는 안 뜨고 5개째에 뜨는지, 그 뒤 6개째에는 안 뜨는지 확인.
   `review_requested_at`을 지우면 다시 뜨는지도 확인. (iOS는 TestFlight/디버그 빌드에서만 항상 뜨고,
   프로덕션에서는 쿼터가 적용된다.)
5. `flutter analyze` 무경고, `flutter test` 통과.
